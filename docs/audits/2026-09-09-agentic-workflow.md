# Agentic workflow and verification audit

Date: 2026-09-09. Scope: the responsive arcade change, duck audit and ticket publication, and the repository tooling used during that work. This combines observed session failures with source inspection. It is not a security audit of every repository script. No per-call token billing is available; cost assessments below are qualitative, not invented token savings.

## Commit and verification status

- Local `dev` contains `11db319c139f391d15e2b1e57ee1fad372f979fb`, `fix(arcade): improve responsive playability and fullscreen controls`.
- A fresh `git ls-remote origin refs/heads/dev` returned `88c374050bd18199fb7a7159c7795eb8f93cb073`. The arcade commit is local and unpushed.
- Fresh `npm run check` passed TypeScript, ESLint, and dependency boundaries: 795 modules, 3,078 dependencies.
- Fresh direct Vitest run: 274 files passed, one failed; 2,321 tests passed and one failed in 43.36 seconds. The failure was the standalone builder's `tsx` IPC pipe being denied by the sandbox. Its complete three-test file passed on an isolated rerun outside the sandbox. This is combined evidence, not a claim that one uninterrupted run passed all tests. The direct run did not invoke npm's `pretest` generator lifecycle.
- The working tree has changes in `lib/design-manifest.ts`, `public/garmin-engine.js`, and `public/monkey-c-mayhem.js`. Formatting both HEAD and working copies with the same Prettier options produced identical output for each file. These are formatting-only differences; they were preserved.
- The duck audit and this report are uncommitted under `docs/audits/`. The docs drift checker rejects untracked files there, so the current tree should not be described as passing all release gates.
- Earlier responsive checks passed 60 Chromium/WebKit viewport cases and six native fullscreen cases. Those results establish their limited assertions, not complete gameplay or physical-device compatibility. Earlier `quality` benchmarking used a running development server and must not be represented as production performance verification.
- Duck defects remain open, including the nested-dialog Escape regression introduced by the arcade commit. The ten findings are documented in [the duck audit](2026-09-09-duck-game.md); implementation tickets are [#598](https://github.com/fderuiter/portfolio/issues/598) through [#605](https://github.com/fderuiter/portfolio/issues/605). Creating tickets did not fix them.

## Findings and recommended changes

Priority P1 means misleading verification or recurring large rework; P2 means recurring friction or avoidable overhead. Suggested owners describe the responsible layer, not assigned people.

| ID | Priority / owner | Evidence and impact | Change and acceptance criterion |
| --- | --- | --- | --- |
| W01 | P1 / tests | `__tests__/build-standalone.test.ts` executes the real builder against repository `public/` paths. Validation rewrites tracked bundles, contaminating subsequent status and commits. | Allow a temporary output directory and run the build test there. Running the suite twice must leave tracked files byte-for-byte unchanged. |
| W02 | P1 / generation | The three current generated-file differences normalize identically. The standalone builder minifies while lint-staged formats all files; generated outputs can oscillate between representations. | Give each generated artifact one canonical formatter and exclude it from competing formatting. Generate, stage, validate, and regenerate with zero additional diff. |
| W03 | P2 / staging | `.lintstagedrc` has overlapping `*` Prettier and TypeScript/JavaScript ESLint-fix globs. Both may write the same file concurrently. Formatting also widened the arcade diff to 828 insertions and 503 deletions across 16 files. | Use one ordered pipeline for code and non-overlapping remaining globs. Repeated staging must be deterministic; review semantic changes separately from necessary formatting. |
| W04 | P1 / verification | `package.json` names `quality` broadly, but it omits unit tests. `verify` invokes static DX diagnostics. Passing either does not establish the entire user journey. | Publish explicit check coverage and provide one complete release command. Its summary must distinguish static, unit, browser, accessibility, and production performance results. |
| W05 | P1 / performance | `scripts/benchmark-pages.ts` accepts any responding target; local `.next` existence substitutes for a valid production build. A live dev server was benchmarked during this task. | Record and validate build mode, source revision, dirty state, target, browser, viewport, and timestamp. Production assertions must reject development targets and absent/stale build provenance. |
| W06 | P2 / server lifecycle | The benchmark starts port 3000 regardless of a custom target URL, hides startup stderr, and waits up to 30 seconds. This makes simple startup errors look like unexplained hangs. | Derive the port from the target and retain startup diagnostics. A deliberately invalid configuration must fail promptly with its actual cause. |
| W07 | P1 / DX diagnostics | `checkSubRoutePerformance` in `lib/dx/doctor.ts` passes when the benchmark file is missing and only rejects routes explicitly marked `passedBudget === false`. Empty/malformed route sets can look successful; freshness is unchecked. | Validate a versioned result schema, expected route coverage, provenance, and freshness. Missing evidence should be reported as not checked, or fail a release gate. |
| W08 | P1 / accessibility | `checkTouchTargetDimensions` scans individual source lines, accepts `h-10`/`w-10` and generic sizing fragments, and treats no same-line `className` as valid. Its success message claims every control meets 48px. | Describe the static heuristic accurately and add rendered, computed-size checks. Include multiline JSX, 40px controls, custom buttons, and responsive overrides as counterexamples. |
| W09 | P1 / browser tests | The responsive suite checked canvas bounds and selected controls. It missed offscreen duck controls and the cabinet Escape handler consuming dismissal before a nested dialog. | Test complete journeys: start, play, read, close, pause/resume, finish, retry, next sprint, and saved progress. Assert control reachability as well as canvas size; implement ticket #605 after prerequisites. |
| W10 | P1 / test model | Ninety-two existing duck tests passed, while nine of eleven targeted audit probes failed. Some engine coverage did not exercise the actual RAF/UI publication path. | Test the public component with a controllable frame clock and observable outcomes. Cover terminal ticks at all four publication phases, next-level state, and 60/120Hz equivalence. |
| W11 | P2 / test design | Two obsolete CSS-string expectations failed only at the first commit attempt, after broader browser work. They required a removed height cap rather than the intended layout behavior. | Run affected tests before broad matrices. Keep source checks only for true architectural contracts; verify layout behavior in a browser. |
| W12 | P2 / hooks and instructions | AGENTS specifies related tests for precommit, but `.husky/pre-commit` runs the entire test suite, generation, security checks, docs compilation, and DX verification. This repeats work after manual validation. | Reconcile documentation and implementation. Use affected checks locally and the complete suite before publication; do not remove the release gate. Any reused result must match exact inputs and revision. |
| W13 | P2 / docs | `scripts/check-drift.ts` recompiles all docs, then treats every untracked file in `docs/` as drift, including authored audit reports. Its regeneration advice cannot stage an authored report. | Distinguish generated drift from unstaged authored content and give specific remediation. Prefer checking generated outputs in isolation; retaining a clean-tree publication requirement is reasonable. |
| W14 | P2 / lifecycle | npm `pretest` regenerates theme and Prisma artifacts; `precompile-docs` regenerates Prisma again. Nested commands hide repeated setup and can mutate the tree during ostensibly read-only checks. | Make setup prerequisites explicit, deterministic, and dependency-aware. Measure each phase and demonstrate that unchanged inputs do not cause repeated writes. |
| W15 | P2 / environment | zsh startup repeatedly emitted fnm symlink permission failures; fnm initialization exists in multiple startup files. Setting `login:false` alone did not help. Bash with `login:false` avoids the noise in this session. | Bootstrap the task shell once and select an available runtime. Fix user shell configuration only with appropriate scope; do not silently change it as part of a repo audit. |
| W16 | P2 / sandbox | `tsx` CLI requires a local IPC pipe even for a short builder, producing EPERM under the sandbox. This caused the fresh suite's only failure. | Use a compatible runtime invocation where supported, or a narrowly scoped approved runner. Classify environment failures separately from product failures and rerun only the affected check. |
| W17 | P2 / agent execution | I read oversized documents and produced truncated tool output, reread context, and sometimes issued independent reads sequentially. Those choices spent context without increasing confidence. | Start with file indexes and targeted `rg`, bound output, batch independent reads, and retain a concise evidence ledger. Read skills when applying them, not speculatively. |
| W18 | P2 / agent iteration | Broad browser matrices were started before representative failures were resolved; duplicate fullscreen and Escape failures then repeated across cases. | Debug one small portrait and one landscape case with fail-fast enabled, then expand the matrix once the cause is fixed. Keep the final cross-browser gate. |
| W19 | P2 / evidence isolation | Source edits, a live HMR server, and browser work overlapped. Reusing live servers and sharing `.next` can make results ambiguous; production builds should not compete with dev runs. | Use a stable test target and record the source state. Separate build outputs or serialize conflicting work; invalidate evidence after source changes. |
| W20 | P2 / run management | A long-running result became unavailable after asynchronous conversation changes. Temporary probes and logs under `/tmp` were useful but are not durable regression evidence. | Persist command, source revision, log path, process identity, exit status, and summary in an ignored run manifest. Promote confirmed defects into permanent tests during remediation. |
| W21 | P2 / browser harness | An axe probe failed because it used a page without the explicit context required by its analyzer path. Cleanup was insufficient and left a pending browser process. | Centralize context creation and `try/finally` cleanup. A deliberately failing probe must close browser and server resources and preserve diagnostics. |
| W22 | P2 / module design | `components/WorkingWithDuck.tsx` is 4,011 lines and couples simulation, frame timing, input, persistence, overlays, and rendering. This makes cheap targeted verification difficult. | Extract coherent lifecycle and persistence boundaries with small public contracts and controllable clocks. Preserve component integration coverage; avoid proliferating thin wrappers that merely move lines. |
| W23 | P2 / reporting | I initially gave canvas and quality passes more weight than their assertions justified. Commit existence, clean worktree, remote publication, and feature correctness are separate facts. | Every handoff should state these four statuses independently, with test scope and known regressions. Never equate ticket creation with remediation. |
| W24 | P2 / audit completeness | Automated viewport checks do not establish real iOS browser-bar behavior, Android font scaling, 200% zoom, screen-reader usability, long-session stability, or whether play feels enjoyable. | Mark these as unverified until exercised. Include manual device and play-session feedback alongside automation; do not fabricate completion from a green matrix. |

## Order of work

1. Resolve the duck lifecycle and Escape defects already ticketed. They affect users and expose the largest verification gaps.
2. Make tests and generators leave the tree unchanged; serialize overlapping formatters. This removes recurring commit cleanup and ambiguous ownership.
3. Correct misleading gate claims and enforce production benchmark provenance. Add counterexamples for missing evidence and touch sizing.
4. Align precommit with documented affected-test behavior while retaining comprehensive publication checks. Measure phase duration before optimizing further.
5. Standardize bounded reads, representative browser probes, cleanup, and durable run summaries. These agent-side changes can start immediately without repository architecture changes.
6. Deepen the duck lifecycle module while implementing the existing regression tickets; verify complete journeys and remaining device/manual scenarios.

## Cost evidence and limits

The first failed commit attempt ran 275 test files before reporting two stale expectations; that run took about 35 seconds. The fresh run in this audit took 43.36 seconds, and only its isolated sandbox failure needed rerunning. The earlier browser matrix provided 60 passing cases while missing critical duck outcomes. These observations show avoidable repetition and misplaced confidence, not a measured token total.

Required approvals, deliberate CRT warmup, independent browser coverage, native blocker verification, and preservation of unrelated edits are useful safeguards. The objective is to remove duplicate or misleading work while keeping evidence that protects users. This audit did not push a commit, change hooks or shell configuration, or implement the duck tickets.
