# Working With Duck audit — 2026-09-09

## Verdict

The game needs functional remediation before it can be considered reliable across devices. The highest-priority problems are progression stalls, lost scrapbook progress, refresh-rate-dependent game speed, and mobile controls that require scrolling away from the playfield.

Audited after commit `11db319` on `dev` (responsive arcade and fullscreen fixes). This is an audit, not a remediation patch. No duck production code was changed during the audit. An Escape-routing regression introduced by that commit is explicitly identified below.

## Evidence and scope

- Existing duck engine, scenario, UI, mobile, and service tests: **92 tests passed across 10 suites**.
- Additional component probes exercised the actual React animation callback and real `stepDuckGame`, with controlled initial states and animation timestamps. **9 of 11 checks failed**, reproducing terminal-state publication, next-sprint startup, retained unlocks, and refresh-rate dependence. Passing controls confirmed victory and failure publication at tick modulo four equal to zero.
- Chromium browser audit: 320×568, 390×844, 667×375, 768×1024, and 1440×900. Launched the cabinet, started Sprint 1, entered fullscreen, inspected playfield/control bounds, seeded saved progress, and ran axe against the active cabinet. No page JavaScript exceptions were observed in these runs.
- Phone and desktop journeys: entered the park, used the whistle, threw the ball with pointer input, returned to the office, entered the bath, scrubbed, rinsed, and finished the bath. These paths completed.
- Tested scrapbook opening, gameplay while reading, fullscreen fallback Escape, and keyboard activation of the Dog Park button.
- Reviewed animation scheduling, input routing, state publication, persistence, progression, mini-game transitions, modal semantics, and existing test coverage.

The prior responsive pass also exercised six cabinets in Chromium and WebKit. The deeper duck-specific probes in this audit used Chromium and JSDOM. Physical iOS/Android devices, 200% text zoom, long-duration endurance, real screen-reader operation, and subjective playtesting were not performed. Browser emulation does not establish thumb comfort or fun.

### D01 — Result panels can fail to appear

Location: `components/WorkingWithDuck.tsx:1864`, especially `1876–1879`; terminal returns in `lib/working-with-duck-engine.ts:771` and `1458`.

The component publishes React UI state only when `nextState.ticks % 4 === 0`. Victory and failure preserve the previous tick counter. If either transition occurs on tick remainder 1, 2, or 3, the engine becomes terminal but React still shows the previous running state. Subsequent animation callbacks do not publish because stepping is conditional on `status === "running"`.

**Reproduction:** initialize the real engine immediately before victory or failure at each of the four tick remainders, mount the component, and drive its animation callback. Both terminal panels appear at remainder 0; neither appears at remainders 1–3. These are six failing cases, not an estimate of their frequency in normal play.

**Impact:** a session can appear frozen with no next-sprint or retry panel. Actions that happen to force a later UI update may mask the problem, but there is no reliable recovery path presented to the player.

**Fix direction:** always publish status transitions and other critical changes immediately; throttle only ordinary HUD updates. Add real component regressions covering every tick remainder for both outcomes.

### D02 — Next sprint looks started but does not simulate

Location: `components/WorkingWithDuck.tsx:3639` and `1633`; `lib/working-with-duck-engine.ts:2716`.

`advanceToNextLevel` returns an initial state with `status: "idle"`. The next-sprint button assigns that object to `gameStateRef`, then changes only the React copy to `status: "running"`. The simulation reference remains idle, so the game loop stops stepping. The win modal's Escape callback uses the same pattern.

**Reproduction:** make Sprint 1 win on a publishable tick, click “Proceed to Sprint 2,” then drive four more animation callbacks. `stepDuckGame` is never called again, even though the UI has transitioned.

**Fix direction:** construct one next-sprint state with the intended status and assign the same state to the engine reference and UI. Cover both the button and Escape path, plus campaign-to-endless transition.

### D03 — Scrapbook progress is lost on launch and advancement

Location: `components/WorkingWithDuck.tsx:1610` and `1810`; `lib/working-with-duck-engine.ts:677` and `2716`.

Fresh game state initializes `unlockedFacts` to `[1]`. The component writes that value to storage but never loads the stored unlock collection. Advancing a sprint preserves accessories, but not unlocked facts.

**Reproduction:** seed `working_with_duck_unlocked_facts` with `[1,2,3,4]`, then launch the cabinet. Storage becomes `[1]` in every audited viewport. Separately, advance a state with `[1,2,3]`; the returned state has `[1]`.

**Impact:** earned collectibles disappear after returning or progressing. This undermines the scrapbook reward loop. The saved high score is read separately and should not be conflated with this confirmed unlock loss.

**Fix direction:** validate and hydrate saved progression before any persistence effect writes; carry cumulative unlocks across sprint changes. Define whether total score is per-sprint or cumulative—the current advancement also resets score, but that product intent requires a decision.

### D04 — Refresh rate changes difficulty and scoring

Location: `components/WorkingWithDuck.tsx:1858`; `lib/working-with-duck-engine.ts:701`.

Each browser animation callback advances the deterministic 60-tick engine exactly once, without considering elapsed time. The component is not using the shared fixed-step arcade loop.

**Reproduction:** drive the real component with 60 callbacks over one simulated second, then 120 callbacks over the same duration. Score after that second is **60 versus 120**. The engine also expresses work progress, need accumulation, and many timers per tick.

**Impact:** high-refresh displays run the simulation faster; slow devices run it slower. Difficulty and scoring cannot be compared consistently between devices.

**Fix direction:** use elapsed time with a fixed-step accumulator, a bounded catch-up budget, and explicit suspension behavior. Verify equal simulation progress at 30, 60, and 120 Hz. Do not simply swap in `WorkingWithDuckEngine`: its current class implementation does not implement the full office/park/bath simulation used by the UI.

### D05 — Controls and playfield do not coexist on short screens

Location: `components/WorkingWithDuck.tsx:2602`, `2802`, and `2917`; duck-specific sizing in `app/globals.css`.

The cabinet now allows scrolling and the canvas fits, but the duck HUD, playfield, and controls still form a tall vertical stack.

**Measurements while the playfield is brought into view in fullscreen:**

| Viewport | Top of Toys/Tricks/Actions tabs | Result |
| --- | --- | --- |
| 320×568 | 584 px | Tabs begin below the screen |
| 390×844 | 615 px | Tabs fit in this tested state |
| 667×375 | 395 px | Tabs begin below the screen |

In landscape the upper HUD is also partially scrolled away. A player must scroll away from the moving simulation to select toys, tricks, or actions, then return to see what happened. The successful earlier canvas-bounds test does not establish simultaneous control usability.

**Fix direction:** give the duck game its own viewport budget: compact HUD and side controls in landscape; a stable, accessible action area in portrait. Preserve touch target size and aspect-correct pointer mapping. Add assertions that an active playfield and essential actions are simultaneously visible, including emergencies and mini-games.

### D06 — Cabinet Escape intercepts modal dismissal

Location: `components/arcade/PlayCabinet.tsx:228`; scrapbook and wardrobe focus traps in `components/WorkingWithDuck.tsx:1654`.

**Reproduction:** enter CSS fallback fullscreen, open the scrapbook, wait for focus to settle, press Escape. Fullscreen becomes false while the scrapbook remains open. Reproduced on phone and desktop layouts.

The cabinet captures Escape before the child modal's handler can dismiss it. This is a regression in the newly committed fullscreen work, distinct from the pre-existing duck defects.

**Fix direction:** give the topmost dialog ownership of Escape and suspend the cabinet focus trap while a child dialog is open. Test nested modal close, focus restoration, and a second Escape to exit fullscreen.

### D07 — Game shortcuts override native button behavior

Location: `components/WorkingWithDuck.tsx:1909`, particularly the Space branch around `1966`.

The global keyboard listener checks whether focus is somewhere in the game container, but does not exclude buttons. It prevents the default Space behavior and executes active coding instead.

**Reproduction:** focus “Dog Park” using the keyboard and press Space. The park does not open. Press Enter on the same button and it opens.

**Fix direction:** preserve native keyboard activation on buttons and other interactive elements; scope gameplay shortcuts to the playfield. Audit all advertised keyboard actions: park throwing and bath scrubbing currently lack a clearly exposed keyboard equivalent to their pointer gestures.

### D08 — Reading a modal does not pause play

Location: `components/WorkingWithDuck.tsx:1617`, `1783`, and `1864`.

**Reproduction:** start a sprint, open the scrapbook, and observe the work meter behind the overlay. It advanced from **2 to 20** during a 1.5-second sample on both phone and desktop. The simulation and music loop do not gate on modal visibility. No pause/resume control is exposed, despite `paused` existing in the state type.

**Impact:** players can miss emergencies while reading instructions or collectibles. Session control is especially poor when they need to scroll to reach a command.

**Fix direction:** establish an explicit pause policy for manuals, wardrobe, scrapbook, background visibility, and user-requested pause. Resume only if play was running before the interruption.

### D09 — HUD contrast fails AA

Location: `components/WorkingWithDuck.tsx:2641`, `2691`, and `2739`.

Axe found three serious color-contrast violations in the visible HUD at portrait, phone, tablet, and desktop sizes. Helper text had contrast **3.84:1**, below **4.5:1**, at 9–10 px. The landscape scan reported none while these labels were scrolled out of view; that is not proof the landscape HUD is compliant.

**Fix direction:** use a higher-contrast text token, then rerun axe with all relevant surfaces visible. Several mobile tab targets are 40 px high, below the repository's 48 px convention; that is a repository ergonomic issue, not a claim that WCAG 2.1 universally requires 48 px.

### D10 — Modals are not announced as dialogs

Location: `components/WorkingWithDuck.tsx:3585`, `3698`, `3735`, and `3851`.

The win, failure, wardrobe, and scrapbook surfaces use generic containers. They have focus traps but lack dialog role, modal state, and a programmatic title relationship. The browser reported zero dialog roles while the scrapbook was visibly open.

**Fix direction:** use a shared accessible modal primitive with a named dialog, appropriate modal semantics, focus containment/restoration, and Escape ownership. Verify with accessibility-tree inspection and a screen reader; axe alone does not establish usable modal behavior.

## Remediation order and acceptance checks

1. **Unblock progression:** D01 and D02. Cover all terminal tick phases, retry, next sprint, and endless handoff through the real component/engine seam.
2. **Protect earned progress:** D03. Reload, remount, advance, and retry must retain intended collectibles. Test malformed storage and storage exceptions.
3. **Make timing consistent:** D04. Equal wall-clock time must produce comparable deterministic state across callback rates, with bounded resume behavior.
4. **Make mobile play continuous:** D05 and D08. Keep core actions with the playfield and add an explicit interruption/pause policy.
5. **Repair input and accessibility:** D06, D07, D09, and D10. Nested dialogs dismiss correctly; Space activates buttons; all intended game actions have usable keyboard paths; visible HUD and dialogs pass accessibility checks.
6. **Validate the complete game:** play through every sprint and both mini-games on Chromium and WebKit, then physical iOS/Android devices. Include orientation changes during dragging, canceled gestures, 200% text zoom, storage reload, background/resume, and long sessions.

## What the current tests miss

Many UI tests assert that classes, tabs, or handlers exist, rather than checking a visible user outcome. Engine-only tests do not catch divergence between the mutable simulation reference and the throttled React copy. The separate `WorkingWithDuckEngine` class is also not the full engine executed by this component, so passing its tests does not validate this gameplay loop.

The earlier responsive matrix remains useful for launch, canvas bounds, and fullscreen exits, but it did not check duck-specific progression, retained rewards, native keyboard button activation, nested dialogs, or simultaneous canvas/action visibility. Those are the key regression seams for the next patch.
